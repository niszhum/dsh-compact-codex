# Agent Note: 交接信息按时间倒序，最新请求压在最前

Status: implemented

## 问题

交接信息原来的段序是「任务起点 → 用户请求轨迹 → 账本主页 → 上一次助手的最后回复 → 文件工作集 → 最近的动作」。新窗口读到的第一段是会话最初那句请求，而它可能已经被改过好几轮——先读起点等于先读一份过时需求，然后才在第 40 行之后发现最近一次修正。多轮会话里这种浪费最明显：那条会话有 21 条真人请求，起点之后的每一条都可能推翻前一条。

## 决策

段序改为时间倒序：最新请求（原话）、上一轮助手回复、账本主页、最近的动作、文件工作集、更早的请求轨迹、任务起点。段序只决定模型先读到什么，**段内列表一律保持旧→新**，不动内部顺序。

新增「最新请求（原话）」段：会话里最后一条真人请求，给原文而不只给索引，上限 800 字符，加入永不裁剪集合。它单独成段之后，请求轨迹只列「起点之后、最新请求之前」的那些，同一句话不占三处预算；只有一条请求时这一段不渲染（它就是起点）。

裁剪顺序仍是「动作 → 文件 → 请求轨迹」，按冗余度定，不跟着段序走。

## 曾考虑的替代方案

**整篇不分段，按事件编号一条线倒序。** 否决。段是检索单元：混成一条线之后，「哪几行是请求、哪几行是动作」要靠读内容判断，新窗口定位成本更高；而且账本主页、文件工作集这类「状态」不是事件，塞进时间线会失真。

**全部倒序，段内列表也倒置。** 否决。动作段倒序会破坏「先做了什么、再做了什么」的叙事，新窗口判断「哪一步是最后一步」反而更慢；请求轨迹倒序则让「任务被改过几次」的演化方向读起来是逆的。段序与段内顺序解决的是两个问题，只动前者。

**起点仍放最前。** 否决。它是验收基准，但不是当前需求；越靠前的段落拿到的注意力越多，把一份可能过期三轮的原话放那里是净损失。

**不新增「最新请求」段，靠轨迹第一行顶替。** 否决。轨迹每条 clip 到 120 字符，只能读到一句话的开头；而最新请求是「现在要做什么」的原文，值得独立的 800 字符。

## 后果

交接信息多一个段头（约 20 token 加原文）。最新请求与任务起点同时出现时，两者之间的差异本身就是有效信息——用户改过什么方向，一眼能看出来，不需要再翻轨迹。

段序由一条离线测试守着（最新请求 < 上一轮回复 < 任务起点 < 收尾指令）。段序与文档 [docs/how-it-works.md](../../../docs/how-it-works.md) 的「交接信息」一节绑定，改一处要改三处（代码、测试、文档）。
