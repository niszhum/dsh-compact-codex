# Agent Note: 交接信息的任务轨迹索引与账本完成判据

Status: implemented

## 问题

换窗后的新窗口靠一份代码拼出的交接信息接着干活。这份交接信息原来只列「最近三条用户请求」，于是多轮会话里最要紧的那句话——会话第一条真人请求，也就是任务的验收基准——会被挤出窗口。用 2026-11-06 的一个真实会话（22 条真人请求）复现：交接信息里出现的请求只有 #1240、#1279、#1293，首条 #11 不在，而该会话的 handoffTokens 预算还剩八成（1841 / 15000 token）。

同一次排查还暴露两个缺口：账本只有 next_step（下一步做什么），没有「做到哪算完」，任务因此会被无限续做；PTC 模式下所有动作都记成 run_code，`meta.diffs` 恒为空，于是「文件工作集」永远是空的，`ledger_append` 这类自指调用也会被当成工作动作列进交接信息。

## 决策

交接信息改为六段：任务起点（首个请求原话，永不裁剪，上限 2000 字符）、用户请求轨迹（起点之后每条请求的编号加一句话，最多 40 条，正文按编号用 history 回查）、账本主页、上一次助手的最后回复、文件工作集、最近的动作。超预算时的裁剪顺序是「最近动作 → 文件工作集 → 请求轨迹」；任务起点、账本主页与最后回复不参与裁剪。

账本新增 `done_when`：一句可判定的验收条件，与 `next_step` 共用「省略即继承、空串即清空」的语义，渲染在主页每个进行中任务下面。

PTC 路径补两处回退：自指调用按参数原文里的 `tools.<name>(` 识别；文件工作集在 diffs 为空时回退到调用参数里认出的写路径（只认写操作，读文件的 file_path 不算）。换窗前的自动快照改记工具结果首行，不再是一句固定文案。

## 曾考虑的替代方案

**只把首条请求单列，请求列表仍保留最近三条。** 信息不够：中途的每一次方向修正都在轨迹里，只给首条会让新窗口把已经被用户改掉的要求当成现行要求。

**把每条动作也做成全量索引。** 否决。同一会话 257 个动作，按每条 20 token 估约 5.1K，占 handoffTokens 上限三成，而值钱的只有失败（11 条）与改动（0 条）两类。动作段维持「最近 12 条 + 截断声明」。

**继续用账本主页的请求段，不单独列轨迹。** 否决。账本主页的请求段是最近三条、每条 400 字符，正是丢首条的那个来源；两处都列又会重复占预算。

**done_when 不新增字段，要求模型写进 text。** 否决。text 是进度记录，自由文本里塞验收条件，代码没法可靠地取出来渲染。

**文件工作集把所有 file_path 都计入。** 否决。读文件也带 file_path，会把「最近被改动的文件」失真成「最近碰过的文件」。

## 后果

交接信息在真实会话上从 1841 token 涨到 2185 token（+19%），仍只占 handoffTokens 15000 的 15%。请求轨迹把「任务被改过几次」变成可回查的编号链，代价是模型多看一眼目录。

`done_when` 由模型填写，质量取决于它当次是否理解了验收标准；代码只能校验类型与长度，判不了内容对错。这一限制接受。

PTC 的路径回退是启发式：正则认不出的写操作（例如把路径拼进变量再传）依然进不了文件工作集。这是已知缺口，等真实会话采样后再改。

模型可见文本里不放计量与配置键名：交接信息的超预算兜底原本写着「超出上限 20000 估算 token」和可调的配置项名，`new_context` 的冷却文案原本报着日志条目数，都已清掉。这条约束随本次交付一并生效，判据是「进模型上下文的话只写模型此刻要做什么」。
