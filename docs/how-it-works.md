## 零摘要换窗

插件继承 `dsh-compaction-basic` 的 `BasicCompactionEngine`，复用它的全部事务机制（日志锁、工具配对边界、压力触发、保留选择、收缩校验），只覆盖基类公开的唯一子类钩子 `summarize()`。

`summarize()` 的实现是**不摘要**：照 Codex 的 token-budget 换窗（`codex-rs/core/src/compact_token_budget.rs`），完全不发起模型调用，直接以一条代码拼出的检查点替换整段历史。

这个取舍解决两个问题：

- **绕开贴顶会话的死结。** 原后端在上下文逼近窗口上限时，摘要请求本身也会超限，形成「为了压缩而发的请求也压不动」的循环。换窗不调模型，从根上绕开。
- **避免两种压缩并存。** 引擎自带的摘要压缩已由本插件在 preset 层接管（替换 `ctx.compaction`），再留一个「本插件也写摘要」的模式只会让两种压缩混在一起。

因此 `style` 只接受 `"reset"`。配其他值会在载入期直接报错，并提示卸载本插件、改用引擎自带实现。

事件流层面的一个细节：换窗结果仍以 `compaction/summary` 的类型记账（类型名来自基类的事务流程，本插件没有改它），差别在内容——本插件写的是以 `# 上下文交接` 开头的交接信息，旧后端写的是模型产出的摘要。

## 交接信息

`reset` 模式落地的那条检查点不是「上下文已重置」这类占位文本，而是一份**代码拼出的交接信息**。思路来自 [ctx-mod](https://github.com/wdsewdser-bit/claude-code-mods)：换窗会丢掉工作细节，所以既不能只丢给模型一句「接着说」，也不能指望模型摘要——后者本身可能出错，还要花钱。

交接信息由四段组成。

**最近的用户请求（原话）。** 从会话记录取真人消息，判据是 `source.kind === 'user'`。`user/message` 这条通道上还走着 `agent-instructions`、`skill-catalog`、`runtime-context`（模型切换通知就走它），以及本插件自己的预算读数——因此这里用白名单只收真人消息，否则新窗口会把系统文本当成权威指令。这一段永不截断，开场白会明确告诉新窗口：记忆与它冲突时以它为准。

**上一次助手的最后回复。** 只给请求和动作说明不了「做到哪了、结论是什么」，而结论通常写在助手正文里。同样是永不截断项。

**文件工作集。** 最近被改动过的文件与其事件编号。路径直接取自引擎已经在 `tool/result` 的 `meta.diffs[]` 里算好的结果，不必从工具参数里解析。

**最近的动作（旧→新）。** 工具名、输入摘要、失败标记、结果首行，每条带事件编号。

超预算时的取舍与 ctx-mod 一致：先砍最近动作，再砍文件工作集；开场白、用户请求与最后回复永不砍——它们承载「用户要什么」与「做到哪一步」。连保底集合都超预算时不再砍，而在结尾注明省略了什么。**截断本身也要显式说出来**：条数上限把动作列表裁到最近 12 条时，列表头部会注明「更早还有 N 个动作未列出」——新窗口看到有限列表会默认它就是全部，更早的已做步骤就会被当成「还没做」重推一遍，这是「换窗后重复执行」的直接推手之一。

规模由 `handoffTokens` 控制（默认 15000 估算 token），内部另有单段的条数上限。

**呈现格式。** 开头是一级标题 `# 上下文交接`，元信息走引用块，四段各用二级标题分隔，结尾用分隔线收束；事件编号与文件路径走行内代码，工具名加粗。这样它在聊天界面里与普通消息一眼可分，否则整条看起来就和平常的一段回复没有区别。这些装饰会随消息进入上下文，但只占几十个 token。

## 客户端渲染

插件同时有浏览器半侧（`lib/client.js`，经 `package.json` 的 `dsh.client` 声明与 `./client` 导出）。它做一件事：把交接消息从引擎自己的压缩行样式里拎出来，交给本插件的渲染器——否则它走的是官方那套「一行灰色小字 + 可展开正文」，展开后是普通文本，看上去和别的消息没有区别。

接法：用 `ctx.uiConversation.events.register()` 注册一个事件定义，`match` 只认内容以 `# 上下文交接` 开头的 user 消息；再把视图注册进 `conversation.chat.node` 这个 keyed slot，key 就是定义里 `buildViewNode()` 产出的 `kind`（`compact-codex-handoff`），它是 renderer key。该 key 与官方注册的十五个（`user`、`steering`、`context`、`compaction`、`manual-compaction` 等）都不冲突。

渲染结果是一张卡片：强调色左边框、一行标题（`上下文交接` + 从交接信息里摘出的首条请求）、展开后是等宽正文。折叠交给原生 `<details>`，组件本身无状态。

两条官方约束已写进代码注释：

- 除 React 基座外，**不 `require` 任何 `dsh-client-*` 包**。它们会变，纯 JS 插件没有类型检查，抛错的组件会清空整个 slot 条目。
- factory 内**不产生副作用**。样式注入放在 `apply` 里由 `ctx.effect` 管理，随插件生命周期装卸。

产物是惰性 CJS factory（`window.__ModuleLoader__.load({ id, factory })`），**手写即最终产物，不需要构建链**。代价是它没有类型护栏，改动时照官方 `cordis-plugin-development` 技能里的 `references/ui-plugin.md` 与 `templates/decoration/` 走。

**编号是真编号。** ctx-mod 需要先把对话逐条写进 `history-wNNN.jsonl` 才能回查；而 dsh 的会话本来就是带 `seq` 的 append-only 日志，`session.eventAt(seq)` 直接取得到，**包括被压缩遮蔽的部分**。所以交接信息可以放心地让模型「按编号回查原文」，不必另存一份历史。

## 预算读数

Codex 把一套上下文管理挂在 `context_management.experimental_mode` 后面，激活门槛是 ChatGPT Plus/Pro 订阅加 codex backend 路由。那是它的商业依赖，不是机制本身。本插件把这套机制拆开、在 dsh 侧重构，不依赖任何服务端能力：

| Codex 的做法 | 本插件的重构 |
| --- | --- |
| 服务端注入 token 预算元数据 | 本地用 `ctx.tokenMeter.measure()` 与 `ctx.llm.resolveModelInfo()` 算出用量与触发阈值，但**默认不注入**：数字只进诊断读数（`budgetContext`，默认关），模型看到的只有压缩点到了这一件事 |
| `guidance_message` / `auto_compact_fallback_prompt`（history notes） | 只在越过阈值那一刻注入换窗指令，不提前催；进度另由账本与换窗前自动快照承接（见「任务账本」） |
| `compact_token_budget.rs` 换窗 | `reset` 模式：不摘要，用代码拼出的交接信息替换整段历史 |
| `new_context` 工具（模型主动换窗） | 注册同名工具；调用只登记请求，在 `agent/pre-step` 消费并调 `compactRegion()` |

注入形态照官方 `dsh-time-context`：prepend 一个 `agent/pre-step` 监听器，先 `next()` 取下游决策，仅在决定进入步骤且未被取消时，往 `decision.messages` 末尾**追加**一条带来源的 user 消息。追加位置在可复用请求前缀之后，因此不会让 KV Cache 失效。

越过压缩点时注入的是这句（不含任何数字）：

```markdown
Context compaction is available now: this window has reached its compaction point.
Do two things in the current turn, in this order.
First call ledger_append: the task id, what is done, and the single next step.
Then call new_context to reset the window — its ledger gate opens once this window has an entry for the current request.
Do not end the turn first: an idle window at the compaction point has no step left to act on it.
```

要诊断时才打开 `budgetContext`，那时才会看到带具体用量的读数（还没有缓存基线时没有第三行）：

```markdown
Context budget as of this step: about 73571 of 676000 tokens used (10.9%).
Automatic compaction triggers near 540800 tokens; roughly 467229 tokens remain before that point.
缓存：活着（前缀约 72k，还剩约 300 秒）
```

注入给模型的有两个时点，都不含数字。

其一是**记账窗口**：离压缩点还剩 `LEDGER_LEAD_TOKENS`（默认 32768）以内就进入窗口，此后**每一个步边界都注入**记账提示（`LEDGER_SOON_REMINDER_TEXT`），直到压缩真正发生。这里不按账本状态收手——账本要的是「压缩那一刻是最新的」，而不是「某一刻曾经新过」，中间新增的动作同样得进去。这一段也必须有：压缩点那一刻根本来不及，基类在本插件的 `next()` 里就已经压完了，提示还没进上下文，窗口已经换掉，模型再想起记账也只能事后追忆。

其二是**压缩点**：越过阈值后注入换窗指令——本回合内先 `ledger_append` 记下状态，再调 `new_context` 换窗（两道账本门槛之一要求本窗口在最新用户请求之后记过账，先记账这一步才走得通），不要先结束回合（空闲的窗口停在压缩点上就没有步边界再去触发压缩）。这一刻起不受节流限制，每个步边界都发，直到压缩真的发生。

两个时点都绑在用量线上、而不是「提前若干 token 泛泛提醒」，是因为空泛的催促会把模型的注意力拉到剩余量上反复计算、收尾停住；记账窗口给的是具体指令（记账），没有可算计的量。

还有一个更靠后的位置：**压前的最后一道闸**。基类的 `pre-step` 监听器在本插件的 `next()` 之内先压、后返回，所以插件的注入点永远落在压缩之后——想让模型在压前记账，只能在压缩真正执行的那一处拦一下。`CodexCompactionEngine` 因此覆写了 `compactIfNeeded`：压力路径且 `ledgerGate` 不通过时先返回 `null` 推迟一步，外层监听器随即把记账提醒送进这一步；下一次步边界照压，不再推迟。推迟额度是**一个窗口一次**，模型不记也不能让上下文一直涨着等它；换窗后标记重置，新窗口有自己的一次。`context-overflow` 触发时不推迟——那是溢出之后的补救，晚一步就是失败。阈值复算与基类公式对齐（`floor(min(W × ratio, W − 预留 − 余量))`），基类改公式时这里要同步。

节流用进程内 `WeakMap` 而不是 `sessionProjections`：插件生命周期与会话同进程，投影会引入额外服务依赖。进程重启后最多多发一条读数，代价可接受。

## 任务账本

换窗会丢掉的不只是历史（历史按编号都能回查），还有模型的意图——交接信息能从会话记录里拼出「做过什么」，但拼不出「打算做什么、为什么这么做、卡在哪」。那部分只在模型的上下文里，不记下来就随窗口一起没了。

记账是模型自己的义务，不是等谁来提醒：每完成一个阶段、定下一个方案、查出一处坑，就在当时记一条。`task_id` 标识任务（同一个任务的多条记录用同一个 id），`status` 取 `in_progress` / `done` / `superseded` / `blocked`，`text` 一句话说要点，未完成时写 `next_step`，并用 `anchors` 记下接下来要改的位置（文件路径加一段能在文件里唯一定位的原文）。

这么定的原因是：账本要在**没有任何催促**的情况下也被写满。压缩点提示只在越过那一刻发一次，靠它来驱动记账，等于把跨窗口保状态的希望压在一条事后补记上——那时模型能想起来的只有最后一段。

两条规则由代码把关，不是模型说了算：

- **标 `done` 必须在 `evidence` 里给出证明它的工具结果编号**，且那个编号必须是真实存在、成功的 `tool/result` 事件（`session.eventAt()` 逐条现查）。拿 assistant 消息或 `tool/call` 的号都会被拒。
- **锚点必须能在文件里唯一定位。** 定位不到的锚点会被丢弃，不会写进账本。

账本落在 `$DSH_HOME/dsh-compact-codex/sessions/<会话 id>/ledger.jsonl`，**不进会话事件流**：它是给模型看的备忘，不该出现在对话里，也不该参与 surface 的配对校验。

`new_context` 有两道账本门槛，任一不成立就拒绝换窗并说明原因：

- 本窗口在最新用户请求之后记过账；
- 最近一次记账之后未记账的工具结果不超过 25 个。

账本还空着时不拦。第一次用没有条目可记，门槛此时不成立。

**压力换窗与冷缓存换窗没有门槛，但有自动快照。** 压力换窗触发时模型正在干活、没机会记账——这是三条换窗路径里最容易带着一长段未记账进度被切走的一条。所以这两条路径在换窗前由代码先落一条 `auto-snapshot` 记录：把最近一段未记账的工具结果归档成一条 `in_progress` 条目，`through` 盖到当前历史编号。快照不是给新窗口的进度描述（那段仍以交接信息的动作段为准），它的作用是把账本时间线钉到换窗点上，让「覆盖边界」双方可见：账本主页渲染时会显示每条记录覆盖到 `#几号`，快照条目的正文也明说「这一段已完成与否以动作段与 history 回查为准，不要凭更早的账本重做」。

**会话摘要缓存。** 门槛、账本主页、快照共享的窗口号 / 真人请求 / 事件摘要，由一次 `snapshotEvents()` 全量遍历统一产出，按 `session.seq` 缓存：seq 不变时同一 pre-step 内的所有检查复用同一份（50 轮实测遍历次数 451 → 50，热路径耗时减半）。会话没有真人请求的窗口（例如刚换完窗、模型接着跑），第一道门槛自动放行。

## 历史检索

交接信息里写着「条目上的 `#编号` 是会话事件编号，用 history 工具回查原文」。`history` 工具是这句话的支撑：

- `search`：按词、`role`、`tool_name`、`path`、`window` 过滤，最新优先；命中处给摘录，并标明命中的是正文、调用参数、工具名还是路径。
- `read`：按编号读原文，支持 `offset` / `length` 分页；`field: "input"` 读那次工具调用的**完整参数**——「不要重跑同样的命令」靠它才有意义。

**它不需要落盘**：dsh 的会话日志本身就是 append-only 的完整历史，`session.snapshotEvents()` 拿得到全部事件（含被压缩遮蔽的），`session.eventAt(seq)` 取得到单条。编号就是事件的 `seq`，因此不必另建一份历史副本再对齐。

窗口维度由换窗事件本身决定：每换一次窗多一条 `compaction/end`，因此这一维不需要另存任何东西，由行的 `seq` 与这些边界算出来。`search` 支持 `window` 过滤，输出里每行带 `W1` / `W2` 这样的前缀，`read` 的头部也标窗口。

## 缓存观测与保活

从 `ctx.tokenMeter` 的 baseline 里读 provider 报的 `cacheReadTokens` / `cacheWriteTokens`，据此知道前缀有多大、缓存还活着没有，并写进读数（见上面那行「缓存：…」）。

这件事的价值在于**换窗的最佳时机正是缓存已经过期的时候**：那时反正要整段重写，换窗不再额外付缓存代价。在此之前这个判断只能靠猜。

**保活默认开启**（`keepalive: true`）。它会在会话空闲时发真实的模型请求（每次只让模型回一个 token）把缓存焐热，**消耗额度**，不需要时可以关掉。规则是：**缓存一旦过期就不救**——那时保活成了整段重写，成本高于等下一次真实请求。保护措施包括前缀下限、每次空闲的保活次数上限、连续失败即停。

**判断保活是否成功。** 看 stderr 里的：

```text
dsh-compact-codex: 缓存保活已发出（第 1 次）；读缓存 75084、写缓存 未报
```

**读缓存大于 0 才算成功**——那说明这次请求命中了已有前缀，是 0.1x 的读；如果是 0，说明它变成了一次整段重写，保活的成本没有省下来。这个数字应当接近会话的前缀规模（可在预算读数的「缓存：…」那行看到）。

保活请求有两条必须遵守的约束：

- **`tools` 要跟着保活请求走。** 工具定义排在请求最前面，属于缓存前缀的一部分；漏掉它们，命中的前缀会短一截，省下的读被一次重写吃掉。
- **计数要在发出之前占位，不能在成功之后。** 检查是周期性的，而 `fire()` 是异步的；等返回才计数，两个周期会同时看到「还没到上限」而各发一次，实际发出数超过 `idleKeepaliveBudget`。

调度以**周期检查**为主（`checkEveryMs`，默认 15 秒），另在 `agent/status` 的 idle 事件上补一次机会。周期检查是主要路径：idle 那条链要三个条件同时成立（事件到达、基线已建立、定时器未占位），断任何一环都不触发，而且失败是静默的。保活是周期性的动作，定时器不挑触发时机，`unref` 也不拖住进程退出。

## 冷缓存换窗

缓存已冷且上下文足够大时，那次请求反正要整段重写前缀，换个新窗口重写不再额外付缓存代价。参考实现把这一步放在「用户下次发消息时」：扣下消息、换窗、再把消息重新提交。

dsh 没有「消息进入前」的钩子（`prompt/submit` 那一类不存在），所以这个时机前移到步开始的决策点：同一套状态、同一套门槛，代价是没有「扣消息再重投」那一步——模型会在同一个回合里继续，而不是等用户再说一次。

它不发起模型调用（换窗走 `compactRegion`），所以默认开着没有额度风险。门槛不满足就静静放过。四个条件同时成立才换：

1. 已经有缓存基线（`lastActivityAt` 非空）；
2. 距上次活动已超过 `cacheTtlMs`；
3. 当前上下文用量不低于 `coldMinTokens`；
4. 账本门槛通过（否则换窗会丢掉没记下来的东西）。
